# API Lab

A free, open-source, browser-based API client, testing, mocking, collection runner, performance testing, and API contract testing platform.

API Lab is being built as a zero-install alternative for everyday API development and QA work — build requests, organize them into collections, manage environments, write tests, run them against mock or real endpoints, and generate reports, all from the browser.

> **Status**: Milestone 12 (Security Hardening & Advanced API Testing) complete. API Lab sends real HTTP requests — GET/POST/PUT/PATCH/DELETE/HEAD/OPTIONS, query params, headers, and raw JSON/Text/XML/HTML bodies — and shows the real response (status, timing, size, headers, Pretty/Raw body views). Requests can be organized into collections and folders, saved, edited, duplicated, moved, and reordered, and the whole workspace persists locally across reloads. Requests can reference `{{variables}}` resolved from a selectable Environment (URL, query, headers, body), with unresolved/circular references caught before send and secret values masked in the UI. Requests can also carry No Auth / API Key / Basic / Bearer / JWT Bearer authorization, with credentials resolved from environment variables at send time and never baked into saved data; OAuth 2.0 is an honest, non-functional placeholder pending its own milestone. API Lab can import Postman Collections (v2.1), Postman Environments, and OpenAPI 3.0/3.1 documents into its own workspace with a mandatory preview step, and export collections as Postman Collections or the whole workspace in a native, versioned, round-trippable format. Requests can carry structured, non-executable **assertions** (status, headers, body, JSON path, response time/size) evaluated automatically after send, plus structured **extractions** that pull a runtime variable out of a response (JSON path or header). A **Collection Runner** executes a collection's saved requests sequentially against a chosen environment, one iteration per row of an imported JSON/CSV dataset (or a single implicit iteration without one), with request chaining, stop/continue-on-failure, and cancellation — with runtime variables scoped per iteration and per run, never leaking between either, and never persisted to disk. A standalone **Mock Server** (`apps/mock-server`, a real Fastify process — the browser can't open its own listening port) lets requests target configurable mock routes with multiple named scenarios (15 built-in status presets, custom headers/body, delay), managed from a "Mock Server" panel in the UI and fully usable as a real Runner/environment target, just like any other HTTP endpoint. A **Performance** workspace runs real load tests: pick a single saved request or a whole collection, an environment, virtual users, duration, ramp-up and aggregate thresholds, then watch live metrics and get a report with RPS, throughput, min/avg/max and P50/P90/P95/P99 latency, status distribution, a seven-way error classification, charts, and JSON/CSV export. Load is generated by a separate local process (`apps/performance-worker`, a Fastify control plane driving a Node worker thread) — **never by the browser tab**, whose per-host connection limits, CORS, and shared render thread would make the numbers misleading. These runs are for development, QA, and controlled staging checks; they are explicitly **not** equivalent to distributed production load-testing infrastructure, and are bounded to ≤100 virtual users and ≤10 minutes with an explicit confirmation before any non-local target. **API contract testing** validates real traffic against an OpenAPI 3.0/3.1 contract (JSON *or* YAML): attach a specification, bind it to a collection, and API Lab resolves each request to its documented operation and checks the request (path/query/header/cookie parameters, body, content type) and the response (status code, content type, declared headers, and full JSON Schema body validation) — reporting precise violations like `$.data.users[2].id — expected integer, received string`. It also detects **contract drift** between a collection and its specification, and reports operation coverage and contract-test coverage as two separate, clearly-defined figures (neither of which is code coverage). Contract results are kept distinct from ordinary assertion results everywhere, including in the Collection Runner. Schema validation uses a pure-interpreter JSON Schema validator with no `eval` or `new Function`, chosen specifically so that an untrusted third-party specification can never become an execution mechanism; schema `pattern` regexes are statically screened for catastrophic backtracking before they are ever run. A **Security / Negative Testing** workspace generates bounded, controlled negative and security tests from a saved request: pick a target, tick the categories you want (missing required fields, invalid types, nulls, empties, boundaries, invalid enums, malformed JSON, unexpected content type, missing/invalid authentication), review a preview of every generated test, and only then start the run. When the request's collection has an OpenAPI specification attached, the mutations are **contract-aware** — required fields, declared types, declared bounds and enums come from the schema, so "send `age` as 17 when the contract says `minimum: 18`" checks a promise the API already made, and both sides of each boundary are tested (17 must be rejected, 18 must be accepted). Responses are checked for sensitive-data exposure, information disclosure (stack traces, database errors, internal paths, framework debug output), configurable security headers, CORS misconfiguration, transport, and 5xx-on-invalid-input robustness, producing findings with severity and concise remediation, plus JSON/CSV export. This is a **QA robustness and security-behaviour testing tool, not a vulnerability scanner**: the set of mutations it can emit is a closed union of nine operations, every substitute credential is a fixed self-identifying constant, and there is no scanning, discovery, enumeration, brute force, or exploitation of any kind (see `docs/SECURITY.md` for the full non-goals list). Runs are bounded to 100 tests and 10 minutes, sent strictly sequentially, and any non-local target requires explicit confirmation naming the host. Reports never contain credentials — sensitive fields are reported by name with the value withheld. Milestone 12 also hardened the contract engine's ReDoS defences: schema `pattern` regexes are now screened by shape *and* by complexity, and then genuinely executed against adversarial probes inside an **isolated Web Worker with a hard timeout**, which is terminated if the pattern does not return — the only mechanism JavaScript offers to stop a runaway regex, and the one that catches patterns static screening provably cannot. Pre-request/post-response scripting remains an inert editing surface — scripts are saved as text but deliberately never executed, pending a dedicated sandboxed-execution milestone (see `docs/SECURITY.md`). See [`docs/ROADMAP.md`](docs/ROADMAP.md) for the milestone plan.

## Running Locally

```bash
npm install
npm run dev              # apps/web on http://localhost:5173
npm run dev:mock-server  # apps/mock-server on http://localhost:4010 (optional, for mock-backed requests)
npm run dev:performance-worker  # apps/performance-worker on http://localhost:4020 (required for the Performance workspace)
npm run typecheck
npm run lint
npm run test        # Vitest unit tests
npm run test:e2e    # Playwright suite (starts the mock server, performance worker, and fixture server itself)
npm run build
```

## Why API Lab

Most capable API tooling today is desktop software you have to install. API Lab's goal is a genuinely browser-first equivalent: nothing to download, nothing to keep updated locally, and an architecture that treats the browser as the primary runtime rather than an afterthought.

This project is an independent implementation with its own name, design language, and codebase. It is not a clone of any existing commercial product, and it does not use their source code, branding, or assets.

## Planned Capabilities

- Build and send HTTP requests (all major methods, params, headers, auth, and body types)
- Organize requests into collections and folders
- Manage environments, variables, and scopes
- Configure authentication (API Key, Basic, Bearer, JWT, OAuth 2.0)
- Write assertions and pre-request / post-response scripts
- Import Postman collections and OpenAPI specs; export to a native format
- Run collections with a Runner, including data-driven runs from CSV/JSON
- Spin up mock APIs with configurable status codes, latency, and error scenarios
- Run performance/load tests and generate functional and performance reports
- Validate requests and responses against an OpenAPI 3.0/3.1 contract, with drift detection and coverage
- Generate bounded, contract-aware negative and security tests (robustness and security-behaviour checks — not a vulnerability scanner)
- Generate API documentation from collections
