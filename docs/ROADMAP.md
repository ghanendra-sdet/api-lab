Milestones are sequential checkpoints. Per `CLAUDE.md`'s Development Workflow, each milestone is Analyzed, Planned, Explained, Implemented, and Validated before being summarized — and the project stops for review after each one. Nothing below is a commitment to a date; it's a commitment to an order.

## Milestone 10 — Performance Engine ✅

- Virtual users, concurrency, duration, ramp-up
- Metrics: RPS, avg, P50/P90/P95/P99, error rate, status distribution
- Performance reports

**Status**: Complete. Shipped `packages/performance-engine` (pure configuration/limits/percentile/aggregation/threshold/report primitives — no React, no DOM, no `node:` imports, because it runs unchanged in both the browser and a Node worker thread) and `apps/performance-worker` (a Fastify control plane on port 4020 that spawns a `worker_threads` Worker per run). Load is never generated in the browser: spec §2 forbids it, and a browser tab's per-host connection cap, CORS, and shared render thread would make any number it produced misleading. The four candidate architectures were evaluated against measurable constraints before implementation and the choice is recorded in `docs/ARCHITECTURE.md`'s Milestone 10 section, including the empirical check that Node 24's TypeScript type-stripping applies to Worker entry points — which is what let the worker follow `apps/mock-server`'s no-build-step convention exactly. Supports single-request and whole-collection targets, fixed-concurrency and fixed-rate load models, duration, ramp-up, think time, per-request timeouts, and cancellation. Virtual users loop the target with a runtime-variable map created fresh per user per iteration, so M8 request chaining works under load and one VU's extracted token can never reach another's request. Environment resolution and API Key / Basic / Bearer / JWT authorization happen browser-side at execution time, so the worker receives only finished header values — never an environment or a credential store. Metrics cover total/successful/failed/aborted requests, error rate, completed and successful RPS (labelled separately, never conflated), byte throughput, min/max/avg and P50/P90/P95/P99 latency by documented nearest-rank percentile, a bounded status-code distribution, a seven-way error classification (4xx / 5xx / timeout / network / connection / cancelled / client), and a per-second time series. Live metrics stream over SSE as a cheap 4Hz `PROGRESS` payload plus a full 1Hz `METRICS` batch, so the UI re-renders once a second no matter how much traffic is flowing. Deterministic aggregate thresholds (P95 / P99 / error rate / RPS etc.) produce a PASS/FAIL verdict — and a cancelled or crashed run is never reported as passed. Reports include a compact summary block, threshold results, an error breakdown, five lightweight hand-rolled inline-SVG charts (no charting dependency), and JSON/CSV export of aggregates only. Safety is bounded by construction: ≤100 virtual users, ≤10 minutes, ≤200,000 requests, bounded retained samples, a re-validating server that never trusts the UI, an explicit confirmation before any non-local target, and no discovery, scanning, or enumeration of any kind. 93 new `performance-engine` unit tests, 27 new `performance-worker` integration tests (a real control plane, a real Worker, a real HTTP target — including cancellation, worker crash recovery, and per-VU chaining isolation), 22 new `apps/web` unit tests, and 16 new Playwright E2E scenarios driving the real UI against the real worker and the M9 mock server — plus the full Milestone 2–9 regression suite (86 E2E tests), unmodified in intent, still passing.

## Milestone 11 — API Contract Testing & OpenAPI Validation ✅

- Validate live responses against an OpenAPI 3.0/3.1 schema
- Contract drift detection between a collection and its spec
- Request/response schema assertions

**Status**: Complete. Shipped `packages/contract-engine` — a pure, framework-independent engine (no React, no DOM, no `node:` imports) that turns an OpenAPI 3.0/3.1 document into a normalized contract model and validates real requests and responses against it. Milestone 6's OpenAPI import code was inspected and deliberately left untouched: the two are different *projections* of the same documents (an importer has no use for `responses`/`components.schemas`; a validator is almost entirely about them), not two ingestion mechanisms. The JSON Schema validator choice was made by reading source, not reputation: **ajv was rejected** because it compiles schemas into JavaScript and evaluates them with `new Function`, which is exactly the "contract schemas must not become an execution mechanism" rule this milestone sets, and which would force `unsafe-eval` into any deployment's CSP; `@cfworker/json-schema` — a zero-dependency pure interpreter with no `eval`, supporting drafts 4/7/2019-09/2020-12 — was chosen instead and is run with short-circuiting disabled so one result reports every useful violation. OpenAPI 3.0 and 3.1 are handled by one dialect (2020-12) plus one explicit, tested translation: `nullable: true` becomes a `["string","null"]` type union (verified necessary — the validator otherwise rejects `null` and every nullable field in every 3.0 document would produce a false violation) and draft-4 boolean `exclusiveMinimum`/`exclusiveMaximum` become the numeric form (otherwise the bound is silently dropped), applied *only* to 3.0 documents. Validation covers request path/query/header/cookie parameters with type coercion, request bodies and content types, response status (exact → `2XX` range → `default`, with undocumented statuses reported rather than waved through), response headers, response content type (parsed properly, so `application/json; charset=utf-8` and `+json` suffixes work and wildcards match), and full JSON Schema body validation with precise `$.data.users[2].id` paths. Operation resolution is deterministic and specificity-ordered — `/users/list` beats `/users/{id}` — and reports ambiguity rather than guessing. Contract drift compares a collection against its bound specification structurally only (never inferring business semantics, never comparing descriptions), with documented severity rules, and coverage reports operation coverage and contract-test coverage as two separately-labelled figures that are never blended and never described as code coverage. Contract validation plugs into the *existing* single execution pipeline after variable resolution and auth, so Send and the Collection Runner behave identically and `{{userId}}` is always resolved before matching; the Runner gained a distinct `contract-failed` status so a contract violation is never collapsed into an ordinary assertion failure. YAML specification support was added (deferred in M6) using the `yaml` package's already-safe default parser. Security work was driven by measurement: `^(a+)+$` against 31 characters was observed blocking the thread for **60 seconds**, so every schema `pattern` is now statically screened and unsafe ones removed with a warning rather than executed. 242 new `contract-engine` unit tests, 38 new `apps/web` unit/integration tests, and 12 new Playwright E2E scenarios driving the real UI against the real M9 mock server — plus the full Milestone 2-10 regression suite (102 E2E tests), unmodified in intent, still passing.

## Milestone 12 — Security Hardening & Advanced API Testing ✅

**Status**: Complete. Shipped `packages/security-engine` — a pure, framework-independent engine (no React, no DOM, no `node:` imports) that turns a saved request into a bounded set of controlled mutations, sends them sequentially, and judges the responses against expectations the tester declares. The scope boundary was treated as the primary design constraint rather than a disclaimer: `MutationOperation` is a **closed union of nine operations**, so "what could API Lab possibly send?" is answerable by reading one type instead of auditing call sites, and there is deliberately no `set-arbitrary`, no payload dictionary, and no free-text injection. Every credential a mutation can install is a hardcoded, self-identifying constant (`api-lab-invalid-token-do-not-honour`, a precomputed JWT expiring in 2001) so a server operator reading their logs can tell instantly that the traffic came from a QA tool — and so credential brute force is structurally impossible rather than merely unimplemented.

Contract-aware negative testing is the headline feature and is qualitatively stronger than body-derived guessing, because a specification carries three facts a request body cannot: which fields are **required**, what **type** each is, and what **bounds** apply. `age: integer, minimum: 18` means the API has already promised to reject `17`, so "send 17, expect 4xx" checks a commitment. The generator emits both polarities of every boundary — `minimum - 1` expecting rejection *and* `minimum` expecting acceptance — which is what catches off-by-one validators, and the integration suite asserts both directions against the real mock server. Where the contract cannot support a claim the generator refuses to invent one: no null mutation for a nullable field, nothing for `anyOf`/`oneOf` branches, and no required-field or boundary tests at all without a schema — each with a warning explaining why, because a negative test that fails against a conforming API is worse than no test.

Response-side checks cover sensitive-data exposure, security headers, CORS, transport, and information disclosure, all built around one rule: **the tool cannot fail a test for something the tester never declared**. Nothing is required by default — a missing `Strict-Transport-Security` on a plaintext internal service is irrelevant, and `Access-Control-Allow-Origin: *` alone is the correct configuration for a public API — so unrequested observations surface as `warning`, never folded into a green pass and never inflated into a failure. Severity stops at `high` (never "critical") and `high` additionally *requires evidence*, enforced in code by downgrading unevidenced findings. Sensitive values are never recorded anywhere: findings name the field and withhold the value, URLs are stripped of userinfo and credential-shaped query parameters, and CSV export neutralises spreadsheet formula injection — a security report is the artifact most likely to be pasted into a ticket, and one that leaked the secrets it found would have caused a bigger problem than it reported.

Safety controls are engine-level rather than UI-level, because a limit that only exists in a dialog is one an automated caller can skip: 100 generated tests, a 10-minute execution ceiling, strictly sequential sending with a pause between requests (M10 owns load generation; §36 forbids this becoming a second, worse one), and a target gate that compares the *approved host* against the *resolved host* — so an approval for staging cannot be reused after a variable resolves to production. Private RFC 1918 addresses are treated as remote, not local. Credentials are never persisted into generated definitions and never resolved until execution time; only test definitions are stored, never results.

**ReDoS hardening (§37)** was the milestone's sharpest finding. Milestone 11's static shape screening was measured to have a real blind spot: `^[a-z]+[a-z]+…[a-z]+$` with ten consecutive quantified groups passes *every* static check — no nested quantifier, no ambiguous group body, ten quantifiers against a limit of twenty, zero group nesting, zero alternations — and was measured **still running after 8 seconds** against a 40-character input, because the ambiguity is distributed *across* the groups rather than contained in one. Two new layers were added: blunt complexity caps, and genuine **Web Worker isolation with a hard 50 ms timeout and `terminate()`** — the only mechanism in JavaScript that can actually stop a running regex, since there is no timeout on `RegExp.test` and no way to interrupt it. Patterns are vetted pre-flight, once per document, against adversarial probes on a disposable thread; anything that does not come back has its worker killed and is refused forever after, so the UI thread never executes it. The three layers are AND-ed, never OR-ed — a `safe` worker verdict does not loosen the static checks. A dedicated test pins the blind spot down so nobody later concludes static screening is sufficient and removes the worker.

The M11 YAML parser configuration was audited against §39 and confirmed already safe (the `yaml` package's default `parse` honours no custom tags and constructs no objects), with nine regression tests added so a future dependency bump that reintroduced tag handling fails the build. The mock server gained six deterministic security fixtures — canned responses, explicitly *not* a vulnerable application, since a genuinely vulnerable endpoint shipped in a developer tool is a genuinely vulnerable endpoint. Test results are now categorised (Functional / Contract / Performance / Security / Negative) and the Collection Runner reports each separately rather than summing them into a number that would mean nothing.

303 new unit/integration tests (222 in `security-engine`, 42 in `contract-engine`, 16 real-HTTP integration tests in `apps/mock-server`, 23 in `apps/web`) and 12 new Playwright E2E scenarios — plus the full Milestone 2-11 regression suite, unmodified in intent, still passing (1111 unit/integration, 126 E2E).

**Status**: Complete. Shipped `packages/documentation-engine` — a pure, framework-independent engine (no React, no DOM, no `node:` imports) that turns an OpenAPI specification, a collection, or both into a normalized documentation model and renders it as a static HTML site, GitHub-flavoured Markdown, or JSON.

The milestone's central decision was how to get at the material Milestone 11 deliberately throws away. `ContractModel` discards descriptions, tags, examples and response descriptions on purpose — its own comment explains that mirroring the whole document would double the memory cost of every attached specification for data the validator never reads — and those are precisely what documentation is made of. Widening it would have reopened a completed milestone with no defect to fix; writing a second OpenAPI parser is forbidden by §6 and would mean two YAML configurations to audit and two chances to disagree about what a document said. Instead M13 became a **third projection**, following the pattern `contract-engine/src/parse.ts` had already established and documented for M6's importer and M11's validator: the source text is parsed **once** by contract-engine's `parseSpecSource`, and that single value feeds `buildContractModel` (structure, normalized schemas, ReDoS screening intact) and `extractOpenApiDocMetadata` (prose, tags, examples) side by side. Milestone 11's code was not modified.

The documentation model is neither the contract model nor OpenAPI, per §4: it is presentation-independent (one model, three renderers), source-agnostic (a collection-only API produces the same shape, so renderers never branch on origin), and safe by construction (every string in it has already been length-capped and redacted — renderers escape, they do not redact). **Provenance is a required field on every fact**, not a document-level flag, so there is no way to add an endpoint or an example without saying whether it came from the specification, a saved request, or a mock scenario — which is how §2's "do not silently invent API behavior" and §7's labelling requirement are enforced structurally rather than by convention.

Source precedence (§5) is stated as *the contract defines, the collection illustrates*, and implemented more strictly than that needs: the merge can only **add** examples to a contract-derived endpoint and only **fill** an absent description, so there is no code path where a collection value replaces a contract value that exists. Collection requests the specification does not document are **kept**, in a labelled "Not in specification" group — dropping them would have turned documentation generation into a way of hiding drift rather than surfacing it. Collection-only documentation observes the honesty constraint throughout: nothing is marked required (a collection cannot know that), no response is synthesised that was not explicitly supplied, and no schema is inferred from an example body.

Recursive schemas (§14) terminate through a **path-scoped** visited set — `User → Manager → User` documents as "User → see User" — where the path scoping is the load-bearing detail: a global set would also collapse the second and third *sibling* use of `Address`, which is not a cycle, producing documentation where most fields are unexplained cross-references. Sibling reuse expands; only genuine recursion terminates, and both the cycle guard and the separate depth cap emit a *stated* node so a reader can tell "this is recursive" from "this is all there is".

Security work centred on the fact that generated documentation is the artifact most likely to leave the machine that made it. `escapeHtml` is the only way a string becomes markup, with no trusted-field shortcut and deliberately **no sanitizer dependency** — §25 permits one, M13 does not need one, so its entire bypass surface is absent. The embedded search index goes through `serializeForScript` instead, because `JSON.stringify` alone is *not* safe inside a `<script>` element: the HTML parser terminates at the literal bytes `</script` regardless of JavaScript quoting, so a description containing `"</script><img src=x onerror=…>"` would break out and execute in a file that passed every other escaping test. The preview never uses `dangerouslySetInnerHTML`; it renders into an iframe with `sandbox="allow-scripts"` and deliberately **without** `allow-same-origin`, putting it in an opaque origin with no access to API Lab's storage, cookies or parent window — so even a total failure of the engine's escaping would confine script to a sealed frame with nothing to reach.

Secret redaction is structural first: `DocAuthentication` and `DocCollectionAuth` have no field a credential could occupy, and the `apps/web` adapter reduces a live `AuthConfig` to type, location and parameter *name* before the engine sees it. The definition of "sensitive" is imported from `security-engine` rather than duplicated. Placeholders are preserved on purpose (`Authorization: Bearer {{token}}` is the useful documentation; the resolved token is an incident), governed by a **closed list of four scheme words** rather than a heuristic, following M12's reasoning for closed unions. The canary suite earned its place immediately: it caught two real leaks during implementation that no unit test of the redactor would have found, because neither value passed through a redactor at all — an OpenAPI parameter's `default`/`example`, which reach documentation through the prose projection rather than through a body, and a collection query parameter's value. Both are ordinary places for an API key to sit and both were being published verbatim; `redactNamedValue` closed them and the canaries now pin it, with a negative control so the suite cannot silently become vacuous.

Output is **deterministic by design** (§33): ids are pure functions of content, every list is explicitly sorted, and there is no counter, no random component and no timestamp — `generatedAt` is opt-in, with a warning in the UI, because a generation timestamp is the commonest way a generator quietly breaks reproducibility. Search (§27, §30) is a flat array of pre-lowercased haystacks scanned with `String.includes` — no Lunr, no inverted index, no server — so the exported page works from a `file://` URL. Only configuration is persisted, never rendered output (§42). Generation is an explicit action rather than a render side effect (§36), and changing the *format* re-renders from the existing model instead of regenerating it. "Try Request" is deferred per §31's own recommendation: the artifact is a document that must work on a machine that has never heard of API Lab, and an execution button would require shipping a second HTTP client into the export.
